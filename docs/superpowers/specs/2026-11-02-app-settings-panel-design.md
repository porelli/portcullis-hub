# App settings panel: template-declared settings, per-person and per-group values

Status: draft for approval (2026-11-02)

Project 1 of 3 (1 settings panel → 2 shared folders + doctor → 3 file
sharing: file-share passwords, Samba, Time Machine). Evidence base:
`.superpowers/sdd/settings-survey.md`. Related specs:
[app instances and domains](2026-11-02-app-instances-domains-design.md),
[certificates self-service](2026-11-02-certificates-selfservice-design.md),
[directory rework](2026-11-01-directory-rework-design.md),
[app updates](2026-11-02-app-updates-design.md).

## Intent

Templates should declare the options an app has, and the Hub should turn
that declaration into a rich settings panel. No per-app Hub code.

Today a template's settings are instance-wide only. There are four types
(text, path, boolean, select). Values go into env or bind mounts, and every
save restarts the instance. Many real needs are per person and come from the
directory, e.g. "people located in Milan get a 10 GB Time Machine
allowance". An admin should be able to:

- see every option an app has;
- set a value per LDAP group (rule-based groups included, e.g.
  `office_milan` with rule `office_location is Milan`), plus a default for
  everyone else who has access;
- see who gets what, and why.

People should see their own values for the apps they can use.

The definition has to cover apps we don't have yet: quotas, roles, budgets,
library access, ACL groups, app passwords. So it is built from a small set
of generic parts (types, scopes, resolution rules, delivery mechanisms, when
a change applies), not from per-app options.

## Goals

1. **One settings definition per template.** Each option declares:
   - its type, constraints and help;
   - its scope: instance, per person, or per group;
   - how the value reaches the app (delivery);
   - when a change takes effect;
   - whether it is a secret.

   The Hub renders the panel, validates the values and delivers them. It
   has no app-specific code.
2. **Per-person options with per-group values.** For a per-person option the
   admin sets:
   - a value for any number of groups;
   - a default for everyone else with access.

   A person in several groups gets the value picked by the option's
   resolution rule (largest, smallest, first in admin order, union, …).
3. **"Who gets what" preview.** Every per-person option shows, for every
   person with access to the instance, the value they get and the reason.
   The preview also works on unsaved edits.
4. **Delivery mechanisms:**
   - env at start (as today);
   - config files the template renders from Hub-written data files;
   - runtime hooks shipped by the template that call the app's admin API or
     CLI;
   - per-person OIDC claims;
   - per-person request headers.
5. **Restart only when needed.** Each option declares when a change applies:
   live, reload, next sign-in, next request, restart, or account creation
   only. The UI shows it before saving. The Hub restarts an instance only
   when a changed option needs it, and folds several changes into one
   restart.
6. **Secrets.** Secret options are write-only:
   - never returned by the API;
   - never in logs, the audit or op records;
   - replaceable, or generated by the Hub.
7. **People page "My apps".** On `people.<domain>`, a signed-in person sees
   the instances they can access, with their own resolved per-person values
   and the reason for each. Nothing about apps they can't access, and
   nothing about other people.
8. **Templates converted.** Every template is converted to the new
   definition. Immich is the pilot: storage quota and role as claims. The
   Time Machine size limit is the motivating example; its template arrives
   in project 3, and the mechanism it needs is built and tested here.
9. **Extension points for projects 2 and 3** are defined (names, shapes,
   contract sections), so those projects add field types and panels without
   reworking this one.

## Non-goals

- Hub-managed shared folders, folder ownership checks and the doctor
  (project 2). File-share passwords, Samba and Time Machine templates
  (project 3).
- People editing their own values (e.g. raising their own quota). People
  only see their values.
- Delegated editing. Delegates (`edit_details` / `invite` / `remove`) have no
  access to app settings.
- Settings for core services (Keycloak, Traefik, group-gate).
- Time-based or scheduled values, and settings history or rollback beyond
  the audit log.
- Changing what an app does with a value. When upstream can't take a
  per-person value (Plex, Vaultwarden orgs, Pi-hole per person), the
  template can't declare one.
- Per-person exceptions for one named person. One-off values use a
  one-member manual group.

## Anti-goals

- **Privilege escalation through the directory.** A delegate with
  `edit_details` changes a field, a rule group gains a member, and that
  person becomes an app admin. Per-group values of privileged options
  (roles, admin flags) must only come from groups delegates can't steer
  (call 9).
- **The default beating a group value.** A default of 500 GB must never
  override `office_milan`'s 10 GB under "largest wins".
- **Leaks across people or apps.** The people listener must never show
  another person's values, nor an app the caller can't access, nor any
  instance-level or secret value.
- **Secret sprawl.** Secret values must not appear on argv, in `docker
  inspect` when avoidable, in logs, in the audit, in op output or in API
  responses.
- **Restart storms.** A membership change (rule groups re-evaluate at most
  every 60 s) must not restart an app for every person who joins.
  Membership-driven deliveries are debounced, and the UI warns when an app
  restarts on membership changes.
- **App-specific Hub code.** Anything one app needs goes into its template:
  a render spec, a data file, a hook.
- **Silent half-application.** A delivery that fails (hook exits non-zero,
  LLDAP write refused) is shown on the instance as failed, with the reason.
  It is never reported as applied.

## Constraints and facts (verified in the code)

- **Settings model today.**
  - `templates.Setting` has `key`, `label`, `description`, `type` (text,
    path, paths, boolean, select), `required`, `default`, `options`,
    `target` (`internal/templates/manifest.go:122-132`).
  - The template schema has the same enum (`tpl-new`
    `schema/manifest.schema.json`, `$defs.setting`). It requires `options`
    only for select.
  - 10 templates have settings (gitea, guacamole, headscale, immich,
    jellyfin, kanboard, matrix, paperless, plex, scrutiny). No template uses
    `paths`.
- **Validation is thin.** `ValidateSettings`
  (`internal/hub/settings.go:106-147`) checks:
  - key shape and control characters;
  - `path` confinement;
  - ports.

  It doesn't check select options, booleans or unknown keys.
- **Delivery today.**
  - text, boolean and select values are written to the instance `.env`
    (`settings.go:319-328`).
  - path values become bind mounts in the Hub override
    (`internal/hub/override.go:42-53`).
  - The `.env` is written 0600 (`internal/hub/env.go:84`).
- **Every save restarts.** `SaveSettings` queues `Restart` whenever the
  instance is enabled (`settings.go:343-346`).
- **Values are echoed.** `AppSettings` returns `Values: h.st.Settings[id]`
  as is (`settings.go:68`). Admin-entered secrets like `HEADSCALE_API_KEY`
  (a `text` setting) come back in plain text.
- **Admin-entered env vars outside settings.** These are `env` entries with
  `generate: none`, with no UI:
  - `CRAFT_VERSION` / `CRAFT_SHA256` in the 15 Craft templates;
  - `COTURN_EXTERNAL_IP` (netbird);
  - `PLEX_CLAIM` (plex).
- **State.** `state.Settings` is `map[string]map[string]string` per instance
  (`internal/state/state.go:102`): flat strings only.
- **Per-person data to apps exists only as shared directory fields.**
  - The Keycloak client scope `portcullis-attributes` carries one
    `attr_<field>` claim per shared LLDAP field, on every Hub client
    (`internal/keycloak/mappers.go:22-24`, `EnsureAttributeMappers`).
  - `user-attributes.json` v1 is keyed by user only, with no host or
    instance (`internal/policy/attributes.go`, contract §4.1).
  - Client copies of `X-Forwarded-Attr-*` are stripped by
    `authResponseHeadersRegex` on every forwardAuth middleware (contract
    §4.1). Routers without forward-auth don't strip them.
- **Immich already names the claims.** `storageQuotaClaim: immich_quota` and
  `roleClaim: immich_role` (`tpl-new/immich/immich-config.json.tmpl:22-23`).
  No mapper emits them, so every user gets the default quota.
  - The config is rendered by `sed` in a start-time one-shot
    (`immich/compose.yml:54-60`).
  - Immich reads the quota and role claims at registration and re-syncs
    them at every login (survey §1.2, docs.immich.app/administration/oauth).
- **Grafana runs auth-proxy** (header-auth, `grafana/compose.yml`,
  `GF_AUTH_PROXY_*`). Today it auto-creates users as Viewer, and "Admin role
  requires manual promotion" (manifest notes). Grafana's auth proxy can read
  a role from a header.
- **Exec has no stdin.**
  - `Hub.Exec` runs `/bin/sh -c <command>` in a running service container
    (`internal/hub/runtime.go:104-133`).
  - The docker client attaches stdout and stderr only, with no stdin
    (`internal/docker/exec.go:28-33`).
  - Output is capped and the process is not killed on timeout.
- **Directory facts.**
  - Rule groups re-evaluate on every change and at most every 60 s
    (contract §9.6, binding).
  - Groups whose rules may reference only admin-only fields: protected
    groups, permission groups and app admin groups (§9.6 "Security rules").
  - `purgeGroup` drops everything `directory.yaml` says about a deleted
    group (`internal/directory/service.go:1508`). App settings live in
    `state.yaml`, which it doesn't touch.
- **People listener.** It serves only `/healthz`, the people page and the
  directory API. It has no app, settings or template routes
  (`internal/httpapi/server.go:76-89`). Contract §5.1.
- **Instances** (contract §11):
  - each instance has its own settings, env, Keycloak clients and groups
    `users_<id>` / `admin_<id>`;
  - templates get `PORTCULLIS_ACCESS_GROUP` / `PORTCULLIS_ADMIN_GROUP`;
  - restore into a new id rewrites hostnames and creates new groups
    (§11.5-11.6).
- **Standing rules.**
  - Prefer mature libraries.
  - No migration or back-compat code: there are no installs, so templates
    are converted, not shimmed.
  - Fail closed.
  - Secrets never on argv, in logs or in the audit.
  - Identity is the LLDAP username, never email.
  - Admin-only and audited management.
  - Contract changes go into `integration-contracts.md` first.
  - Templates stay declarative.
  - `Hub.mu` is never held across network calls.

## Decided by the user

- Templates define configurable variables that the Hub turns into a richer
  settings panel.
- Values can come from LDAP/the directory, e.g. "people located in Milan
  have 10G allowance for Time Machine". It has to be flexible enough that
  new apps and options don't need ad hoc work, and forward-looking for apps
  we don't have yet.
- The admin sees all of an app's configurable options and can set limits for
  an entire LDAP group (e.g. the rule group `office_milan`).
- The approved mockup direction:
  - general (instance-wide) options;
  - per-person options with per-group values and a default for "everyone
    else with access";
  - a resolution rule for people in several groups;
  - a "who gets what" preview with the reason.
- "The settings panel definition is flexible enough for all the different
  apps."
- Individual users see app-specific things (e.g. their file-share password,
  project 3) on their People page under My apps → <app>, shown only when
  relevant (they have access).
- The split into three projects in this order: settings panel → shared
  folders + doctor → file sharing.
- No per-person exceptions: one-off values use a one-member manual group.
- People page My apps: YES, a person sees which group gave them a value
  (the `reason.group` field in `/api/me/apps`), but only groups they are a
  member of — the resolved reason's group is always one they belong to.
  Losing groups (e.g. in "largest of …") are never shown; the full
  breakdown stays in the admin preview.

## Calls made while drafting (check these)

Items marked **Controller's call** were made by the controller during the
brainstorm. The others were made while drafting this spec.

1. **Default = fallback only.** *(Controller's call.)* The default applies
   only to people in none of the groups that have a value. It never takes
   part in max/min/union.
2. **Resolution chosen per option by the template.** *(Controller's call.)*
   The template declares `resolve`, and may list `resolve_choices` the
   admin can switch to. Rules:
   - `max`, `min`: int, size, duration, enum by option order;
   - `priority`: any type; the admin orders the group rows, and the first
     row that matches wins;
   - `union`, `intersection`: list, multi_enum, groups;
   - `any`, `all`: bool.

   `unlimited` (where allowed) beats any number under `max` and loses under
   `min`.
3. **Admin-only, audited.** *(Controller's call.)* Settings are read and
   edited only on the Hub listener, by admins. Every change is audited as
   `settings.change` with:
   - instance and key;
   - scope and group;
   - before → after (secrets: "replaced");
   - the actor.
4. **People see their own resolved values.** *(Controller's call.)* Only
   for instances they can access (call 15).
5. **Each option declares when it applies.** *(Controller's call.)* Levels:
   - `live`: a hook applied it;
   - `reload`: the template's `reload:` action (call 25);
   - `next_sign_in`;
   - `next_request`;
   - `restart`;
   - `account_creation`: only new accounts get it; the UI warns "existing
     accounts keep their value".

   On save the Hub runs only the strongest effect among the options that
   changed. The UI shows that effect before saving ("Saving restarts
   Immich" or "Takes effect at each person's next sign-in, no restart").
6. **Field types.**

   | Type | What it holds |
   |---|---|
   | `string` | `pattern`, `min_len` / `max_len`, `format`: hostname, ip, cidr, url, email, iana_tz, locale, cron, semver, hex. Formats give pickers without app code |
   | `int` | `min` / `max` / `step`, a `unit` label |
   | `size` | Canonical bytes; binary units in the UI (MiB/GiB/TiB, labelled so); `step`; `allow_unlimited` |
   | `duration` | Canonical seconds; `min` / `max` |
   | `bool` | True or false |
   | `enum` | `options[{value, label}]`; the order is the rank |
   | `multi_enum` | A set of options |
   | `list` | Items of a scalar type; `min_items` / `max_items`, `unique` |
   | `table` | Records with typed scalar `columns`, optional `key` column |
   | `path` | A host path with `target` and `mode: ro\|rw` |
   | `secret` | Write-only |
   | `group` / `groups` | LLDAP group names |
   | `user` / `users` | LLDAP usernames, never email |

   - The old type names are dropped: `text` → `string`, `boolean` → `bool`,
     `select` → `enum`. `paths` is removed.
   - Ports stay in the top-level `ports:` block, unchanged.
   - Reserved names for later projects: `folder` (project 2),
     `person_secret` and `person_id` (project 3). They are in the schema with
     their shapes (call 20). A Hub that doesn't implement a type refuses the
     template with a clear reason (fail closed).
7. **Scopes.**
   - `instance`: one value.
   - `person`: resolved per person from the default and the per-group
     values. It needs a `default` and at least one per-person delivery
     (claim, header, file or hook). Per-person env keys are not allowed.
   - `group`: one record per group the admin adds, not resolved per person.
     Used for app-resolved maps: library or ACL per group, rooms per group.
     It is delivered as a map through env (JSON), a file or a hook.
     Implemented and tested with fixture templates. No template is
     converted to it here.

   The people a `person` option applies to are the members of the
   instance's access group, or every signed-in user when the instance has
   none. Call 27 spells this out for path groups, public routes and
   `sign_in: native`.
8. **Option keys are identifiers, not env names.**
   - Keys match `^[a-z][a-z0-9_]{0,39}$`.
   - An env delivery names its variable (`env: IMMICH_TRASH_DAYS`).
   - An instance option with no `delivery` defaults to env, under
     `upper(key)` as the variable name.
   - The validator refuses:
     - env names that are reserved (`ReservedVar`, `PORTCULLIS_*`) or
       hard-coded in `compose.yml`;
     - duplicate env names.
9. **Privileged options.** An option marked `privileged: true` (role, admin
   flag) may take per-group values only from groups delegates can't steer:
   - manual groups;
   - rule groups whose rules reference only admin-only fields.

   Adding such a group to a privileged option makes it an "app admin group"
   for the §9.6 security rules. Its rule then can't gain a non-admin field,
   and it can't match an empty account. The picker shows the other groups
   greyed out, with the reason. The default of a privileged option must be
   its lowest-ranked value. Call 28 covers where this is stored and which
   guarding rules apply.
10. **Template-declared starting values.** `group_values` in the template
    gives starting per-group values, written when an instance is created
    (e.g. Immich role: `{{ADMIN_GROUP}}: admin`).
    - Only the placeholders `{{ACCESS_GROUP}}` / `{{ADMIN_GROUP}}` are
      allowed; literal group names are refused.
    - The Hub stores references to the instance's own groups as these
      placeholders. Restore into a new id therefore points at the new
      instance's groups without rewriting.
    - A restored reference to a group that no longer exists is dropped,
      with a restore warning.
11. **Rendering per delivery.**
    - Values are stored canonical (bytes, seconds, typed JSON).
    - Each delivery has its own `render`:
      - `unit`, with integer output;
      - `unlimited` sentinel;
      - `true` / `false` strings;
      - `join`;
      - `format: json|yaml|csv`.
    - A value that doesn't fit a delivery's granularity (1.5 GiB into an
      integer-GiB claim) is refused at save. The error names the app and its
      unit. The UI enforces `step` up front.
    - The Hub does all quoting and escaping. Env values never contain
      newlines (structured values use `format: json`).
12. **Claim delivery: Hub-managed LLDAP attributes and per-client mappers.**
    - For each (instance, option) with a claim delivery, the Hub creates a
      Hub-owned LLDAP user attribute:
      - STRING type, not visible, not editable;
      - named `ps_` + a short hash of instance and key;
      - never a custom field: Users & Groups hides `ps_*` attributes.
    - The Hub writes each person's rendered value into it.
    - It adds an LDAP attribute mapper, plus a protocol mapper **on that
      instance's client only**, with the template's claim name and JSON
      type (`int`, `string`, `bool`, `json`). This is like
      `EnsureAttributeMappers`, but per client.
    - People outside the option's population have the attribute cleared.
    - Claim names may not collide with standard, Portcullis or `attr_*`
      claims (validator list).
    - Removing the instance removes its attributes and mappers.
    - Reason: Keycloak has no per-group claim mapper without scripts.
    - The builder may propose Keycloak-local attributes on federated users
      instead, if they verify these survive LDAP sync in READ_ONLY mode.
13. **Header delivery: per-host headers in `user-attributes.json` v2.**
    - The file gains a `hosts` section: full hostname → header map → users
      → values.
    - group-gate (core) returns those headers on allow for that host only.
    - Header names must be `X-Forwarded-Attr-<Name>`, so the existing
      strip regex covers them.
    - Allowed only on forward-auth and header-auth routers. The Hub refuses
      header delivery for templates whose routers lack forward-auth.
    - Pilot: Grafana role (`GF_AUTH_PROXY_HEADERS` `Role:` mapping), ranked
      enum Viewer < Editor < Admin, `privileged`, `applies: next_request`.
    - Grafana's role sync: see call 30. The core change and multi-host
      instances: see call 26.
14. **File delivery: Hub-written data files the template renders.**
    - A template declares named `files:`, each with a `service` and a
      container `mount`.
    - The Hub writes `<instance>/<name>.json` under its data dir:
      - contents: version, instance values, per-person rendered values
        keyed by lowercase username, per-group records;
      - written atomically, 0600 when it holds a secret, else 0640;
      - bind-mounted read-only into that service by the override. The
        override mounts the instance's data-file **directory**, never a
        single file. An atomic rename on the host gives the file a new
        inode, and a single-file bind mount keeps showing the old one
        until the container restarts, so a reload or hook would read stale
        data. `mount` is therefore a container directory, and the file is
        `<mount>/<name>.json`.
    - The template's init one-shot renders the app's config from it, the
      way Immich's `sed` step does today.
    - Secrets go into a separate file per instance, never into a file that
      holds no secret.
    - Per-person file delivery (the Time Machine case) is proven in CI with
      a fixture template.
15. **"My apps" on people.<domain>.** *(Builds on Controller's call 4.)*
    - A new tab beside People / Groups / Org chart.
    - A new people-listener route `GET /api/me/apps` (contract §5.1)
      answers for the caller (`X-Forwarded-User`) only: enabled instances
      whose population includes them, each with the name, link and their
      per-person values (label, displayed value, reason, when it applies).
    - This is a deliberate exception to the rule that the people listener
      registers no app or settings routes (CLAUDE.md,
      `TestPeopleListenerHasNoAppRoutes`). It is the only such route, it is
      read-only, and it answers only about the caller. The test gets an
      allowlist containing exactly this route, and contract §5.1 is changed
      first.
    - Options marked `self_visible: false` are left out. The default is
      visible.
    - Instance options, secrets and other people are never included.
    - Project 3 adds per-person credential panels in the same place (call
      20).
16. **Hooks (runtime API delivery).**
    - A template declares `hooks:` with:
      - `name` and `service`;
      - `command` as an argv list, run directly, not through `sh -c`;
      - `when`: any of `start`, `settings_change`, `membership_change`;
      - `timeout`.
    - Options deliver with `hook: <name>`.
    - The Hub runs the command in the service's running container and sends
      the **full desired state** as JSON on stdin (instance values,
      per-person values, group records, secrets), never a diff. Docker
      exec gains stdin.
    - Hooks must be idempotent. Exit 0 means applied. Anything else is
      "failed", recorded in the instance's op record. Known secret values
      are redacted from the output first, then it is clipped (redact, then
      clip: never the other way round).
    - Runs per instance are serialised. A failed run is retried on the next
      trigger, and the admin can retry it from the panel.
    - Pilot: Nextcloud instance options applied live through `occ`
      (default quota, trash retention) instead of the start-time
      `setup.sh` only. Builder may pick another live pilot.
17. **Membership changes.**
    - After each directory reconcile, the Hub recomputes resolved values
      and updates only deliveries whose output changed:
      - claims: LLDAP attribute writes;
      - headers: the attributes file;
      - files: re-render;
      - hooks: run with `membership_change`.
    - The work is debounced per instance. Default 60 s, matching the rule
      cadence.
    - A file delivery declares `on_membership_change`: `restart`,
      `reload`, `hook` or `none`. With `restart`, the panel warns "people
      joining or leaving restarts this app".
18. **Secrets.**
    - `secret` options:
      - GET returns `{set, updated_at}` only;
      - PUT accepts a new value, or `generate` when the template declares
        `generate: {length, charset}`;
      - clearing needs an explicit action.
    - Delivery: env (in the 0600 `.env`; the template accepts `docker
      inspect` visibility), file (the secrets file, call 14), or hook stdin.
      Never argv.
    - Redacted from logs, the audit, op output and backups' plain metadata.
      Backups carry them as they carry the `.env` today.
    - `env:` entries with `generate: random` stay as they are: internal
      generated secrets, not settings.
    - `env:` entries with `generate: none` become settings:
      - `secret`: `PLEX_CLAIM`;
      - `string` with a format: `COTURN_EXTERNAL_IP`, `CRAFT_VERSION`,
        `CRAFT_SHA256`.
19. **Groups disappear cleanly.** Deleting an LLDAP group through the Hub
    also purges per-group values and `group`-scope records that reference
    it, in every instance. The purge is audited, and the affected instances
    re-deliver. Re-creating the name inherits nothing, like `purgeGroup`.
    This also holds for groups deleted outside the Hub: see call 29.
20. **Extension points for projects 2 and 3.** Defined here, implemented
    there.
    - **`path` ownership** (used now, checked by project 2's doctor): a
      `path` option may declare:
      - `writes_as: {uid, gid}`, numbers or references to other option
        keys, e.g. `PUID`;
      - `needs: read|write`.

      Project 1 validates these and shows them in the panel ("the app
      writes here as 1000:1000"). All converted path options declare them.
    - **`folder` type** (project 2): the value is the id of a Hub-managed
      shared folder. It resolves to the folder's host path, mounted at the
      option's `target`. Ownership comes from the folder, checked against
      `writes_as`.
    - **`person_secret` type** (project 3): a per-person credential issued
      by the Hub.
      - Fields: `hash: nt|bcrypt|sha512_crypt|argon2id`, `length`,
        `delivery: file|hook`, `revoke_on_leave: true`.
      - Shown once on My apps → <app> after a fresh passkey touch (the
        certificates spec's fresh-authentication pattern). Stored only as
        the hash, in the instance's private storage.
    - **`person_id` type** (project 3): a stable integer the Hub allocates
      per person and instance from a declared range. Never reused, and kept
      across restore.
    - **My apps panels:** the `GET /api/me/apps` entry has a `credentials`
      list that is empty in project 1.
21. **Template contract v3** (breaking: MAJOR bump).
    - The contract gets a new section "§13 Settings": types, scopes,
      resolution, deliveries, data-file and hook-input formats, `applies`
      levels.
    - It also changes:
      - §4.1: `user-attributes.json` v2;
      - §5.1: the `/api/me/apps` route;
      - §8: per-client setting mappers.
    - The schema and `validate.py` in the templates repo enforce the same
      rules as the Hub, including the cross-checks:

25. **The `reload` mechanism.** *(Controller's call.)* Survey §"Restart vs
    live" proposed `reload: {signal: HUP}` or `{exec: [...]}`.
    - A template declares at most one top-level `reload:`, in one of two
      forms:
      - `{service, signal}`, where `signal` is one of `HUP`, `USR1`,
        `USR2`;
      - `{hook: <name>}`, naming a declared hook. It gets the same stdin
        and exit-code rules as call 16.
    - `applies: reload` on an option, and `on_membership_change: reload` on
      a file, are refused by the validator (Hub and `validate.py`) unless
      the template has a `reload:`.
    - Signal form: the Hub sends the signal through the Engine API
      (`POST /containers/{id}/kill?signal=…`, a new `ContainerKill` in
      `internal/docker`). `socket-proxy-hub` already allows it
      (`CONTAINERS` + `POST`), so the core proxy needs no change.
      - It counts as applied when the call returns 2xx and the container
        is still running after a 10 s grace period. If the container has a
        healthcheck, it must also not be unhealthy.
      - Otherwise it is "failed", in the op record.
      - The panel says "reload signal sent, app still running", never "the
        app accepted the change". Templates should use the hook form when
        the app can confirm through its exit code.
    - Data files are written before the reload. If the instance isn't
      running, nothing is sent, because the next start reads the files.
    - The order used to pick the strongest effect on save: `live`,
      `next_request` and `next_sign_in` need no action, then `reload`, then
      `restart`. Several reloads in one save, or in one debounce window,
      become a single reload.
26. **The core (group-gate) change is in scope.** *(Controller's call;
    calls 13 and 21 already commit to it.)*
    - group-gate reads `user-attributes.json` v2 only (no v1 fallback,
      since there are no installs). On allow it returns the `hosts`
      headers for the request's host, next to the existing per-user
      field headers.
    - Order of work: contract §4.1 first, then the core group-gate change
      and its tests, then the Hub, then the templates. CI already clones
      the same-named branch of core and templates, so the four branches
      are tested together. Core is merged before the Hub.
    - Multi-host instances: the Hub writes the header map under **every**
      host of every router of the instance that runs `portcullis-groups`.
      That includes extra-domain hosts, because `portcullis-auth-ext`
      chains still pass through group-gate and strip `^X-Forwarded-Attr-`.
    - Public routes: requests on a public router (a public exception, or
      `public@file`) don't go through group-gate and aren't stripped. So
      the validator refuses header delivery when the delivering service
      also has a router the template marks public, and the Hub refuses
      `sign_in: native` together with header delivery. Otherwise a client
      could forge `X-Forwarded-Attr-*` on a public path.
27. **Who is in a person option's population.** *(Controller's call.)*
    The population is the people group-gate or the access role would let
    in on the instance's signed-in routes:
    - With an access group (group access on, or an access role enforced):
      its current LLDAP members, minus anyone in an expired-but-not-yet-
      removed entry of the published `expiring` list (group-gate already
      denies them).
    - Without one (group access off): every LLDAP user except the service
      account.
    - Admin path groups (`admin_<id>`), extra groups and core groups never
      widen the population. A member of `admin_<id>` who isn't in the
      access group can't reach the app, so gets nothing.
    - Public hosts and public exceptions add nobody. Anonymous visitors
      aren't people.
    - `sign_in: native`: the population is empty. Portcullis passes no
      identity, so per-person deliveries are cleared, and the panel says
      "per-person values need Portcullis sign-in".
    - A disabled instance keeps its population for the preview, but
      delivers nothing and isn't on My apps.
28. **Privileged-option groups are app admin groups, computed on the fly.**
    *(Controller's call.)* No new `directory.yaml` field.
    - `directory.App` (the `Service.Apps` callback) gains a list of the
      instance's privileged groups: every group named in a row of a
      `privileged` option. `guardingGroups` adds them with the reason "a
      privileged value of app <id>".
    - They get exactly the guarding behaviour `admin_<id>` gets today, no
      more:
      - rules on admin-only fields only (409);
      - no rule that matches an empty person;
      - the evaluator never adds `created_by` accounts;
      - an admin-only field they use can't be turned off (`fields.go`);
      - "became guarding later" is handled by `addsBlocked`.
    - Removing the row ends the guarding at once, because nothing is
      stored.
    - The delegate target rules are unchanged. Delegates may still edit
      the details of members of `admin_<id>` today, and that is no
      escalation. A delegate can change only non-admin-only fields, which
      no guarding rule reads, and only admins add members to manual
      groups.
    - The Hub re-checks the group rule at save (400), not only in the
      picker.
29. **Groups deleted outside the Hub.** *(Controller's call.)*
    - Each per-group row and each `group`-scope record stores the LLDAP
      group id (`lldap.Group.ID`) it was set against. Placeholder rows
      resolve the id when the instance is created or restored.
    - Resolution matches by name **and** id. A row whose group is missing,
      or now has another id (deleted in LLDAP and re-created), grants
      nothing from that moment.
    - The next directory reconcile that sees it purges the row, audited as
      `settings.purge` with actor `hub`, and re-delivers. The re-created
      group inherits nothing, even within the reconcile window.
    - Restore applies the same check, and drops rows whose id no longer
      matches with a restore warning (call 10).
30. **Immich and Grafana role sync.** *(Answered from upstream docs, plus
    a Controller's call for Grafana.)*
    - Immich (docs.immich.app/administration/oauth, checked 2026-11-02):
      "Claims are applied when a user is first registered. On subsequent
      logins, claims present in the OAuth profile are synchronized". That
      covers quota and role. The exception is the storage label. So
      `applies: next_sign_in` stands for both, and the e2e checks a
      changed role on an existing account. Claims that are absent are
      left unchanged, which is harmless: people outside the population
      also lose the access role.
    - Grafana: the template sets `GF_AUTH_PROXY_SYNC_TTL: 0` ("always
      fetch and sync the latest user data") and maps
      `Role:X-Forwarded-Attr-Grafana-Role`, with `applies: next_request`.
      The upstream page doesn't say whether a header role updates an
      existing user. If the e2e shows it doesn't, the option is declared
      `applies: account_creation` (warning shown) and the e2e asserts on a
      new account. No hook fallback.
31. **`requires` (Craft version pin).** *(Controller's call, from survey
    §1 and `tpl-new/*craft/fetch.sh`.)*
    - `requires: [<key>, …]` on an instance option: when this option is
      non-empty, every listed option must be non-empty too.
    - The Craft pair declares it both ways, so both are set or both are
      empty. Empty means the pin in `compose.yml`
      (`${CRAFT_VERSION:-…}` treats empty as unset).
    - Types:
      - `craft_version`: `string`, pattern `^[0-9]+\.[0-9]+\.[0-9]+$`;
      - `craft_sha256`: `string`, pattern `^[0-9a-f]{64}$`.
    - Validator: the listed keys exist, there is no self-reference, and
      the keys are instance scope only. A save that breaks it is a 400
      naming both options. The panel shows the pair together.
    - Changing the version is `applies: restart`. The `<app>-fetch`
      one-shot downloads and verifies the release at every start. There is
      no image re-pull and no rebuild.
    - `requires` joins call 6's constraint list and call 21's schema
      cross-checks.

Immich (pilot; abridged):

```yaml
settings:
  sections: [Storage, Accounts, Library]
  options:
    - key: trash_days
      label: Keep deleted items for
      type: int
      unit: days
      min: 0
      max: 3650
      default: 30
      scope: instance
      section: Library
      applies: restart
      delivery: [{env: IMMICH_TRASH_DAYS}]     # rendered into config.json at start
    - key: storage_quota
      label: Storage quota
      type: size
      step: 1GiB
      allow_unlimited: true
      scope: person
      default: 100GiB                          # everyone else with access
      resolve: max
      resolve_choices: [max, min, priority]
      section: Storage
      applies: next_sign_in
      delivery:
        - claim: {client: immich, name: immich_quota, json_type: int,
                  render: {unit: GiB, unlimited: "-1"}}
    - key: role
      label: Role
      type: enum
      options: [{value: user, label: User}, {value: admin, label: Administrator}]  # order = rank
      scope: person
      privileged: true
      default: user
      group_values: {"{{ADMIN_GROUP}}": admin}
      resolve: max
      section: Accounts
      applies: next_sign_in
      delivery: [{claim: {client: immich, name: immich_role, json_type: string}}]
    - key: external_library
      label: External photo library
      type: path
      mode: ro
      needs: read
      writes_as: {uid: 0, gid: 0}
      target: {service: immich-server, mount: /usr/src/app/external}
      scope: instance
      applies: restart
```
